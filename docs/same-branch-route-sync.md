# Same-branch route-map synchronization

Cross-repository route changes must be reviewable before any member of the
change set reaches `main`. The workflow generated by `scripts/install-into.py`
therefore resolves every configured sibling repository at the current branch
name first and uses `main` only when that branch does not exist.

## Resolution contract

For every `--checkout owner/repository` entry, the generated workflow:

1. derives the requested sibling ref from
   `${{ github.head_ref || github.ref_name }}`;
2. queries the GitHub Branches API for that exact ref;
3. selects it only after a successful response;
4. falls back to `main` only after an explicit `404` for the matching ref; and
5. fails closed for authorization failures, API failures, or an unreadable
   fallback.

A fallback is not silent. The resolver emits a workflow warning and appends a
JSON Lines record to `.ridl/sibling-resolution.jsonl`. If the route checker
then fails, the generated workflow prints that record beside the failure. This
distinguishes product route drift from a coordinated sibling branch that has
not yet been pushed or merged.

The route checker itself is unchanged: maps, handlers, generated clients,
transport bindings, and authored schema authorities still have to agree.

## Workspace layout

`actions/checkout` requires checkout paths under `$GITHUB_WORKSPACE`. The
generated workflow uses this deterministic side-by-side layout:

```text
$GITHUB_WORKSPACE/
├── source/                 # exact triggering repository revision
├── sibling-api-server.rs/  # example sibling checkout
└── sibling-lib-core/       # example sibling checkout
```

Commands run from `source/`, so existing route-sync source paths such as
`../sibling-api-server.rs/src` continue to work without escaping the Actions
workspace.

## Authentication

Public sibling repositories work with the workflow token. Private or internal
siblings can provide an organization or repository Actions secret named
`ROUTE_SYNC_GITHUB_TOKEN`. Use a dedicated least-privilege token that can read
only the required repositories. The generated workflow falls back to
`${{ github.token }}` when the secret is absent.

The resolver deliberately treats non-`404` API responses as errors instead of
pretending a branch is missing. If neither the requested branch nor `main` can
be read, synchronization stops.

## Coordinated change procedure

Use the same branch name in every repository participating in one route
contract change, for example:

```text
DEN-4078-cross-repo-route-contract
```

Regenerate each consumer workflow from `api-docs/scripts/install-into.py`, push
all sibling branches, and then open the related pull requests. Each PR will
compare its own route map and handlers against the matching sibling branches.
A repository without the coordinated branch is checked against `main` and
reports that fallback explicitly.

## Installer example

```sh
python3 scripts/install-into.py ../consumer-lib-core \
  --maps route-maps/api.route-map.json \
  --sources ../consumer-api-server.rs/src \
  --checkout Example/consumer-api-server.rs
```

Do not hand-edit the generated workflow or vendored resolver. Re-run the
installer so `scripts/vendor/MANIFEST.json` records the exact toolchain files.
