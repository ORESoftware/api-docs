# Web-server page generation boundary (draft)

This document is intentionally scoped to `*-web-server.rs` and `*-admin-web-server.rs`. It does **not** redefine the `*-api-server.rs` / `*-admin-api-server.rs` route or RPC contract.

## Goals

1. Keep a Next.js-like 1:1 relationship between browser URL paths and Rust source folders.
2. Generate deterministic page documentation from authored Rust attributes without executing page code.
3. Keep `gen.rs` exclusively on the web-page/static-generation side.
4. Let `ores-stack` project an admitted page inventory into monolith, static, or Lambda deployment shapes without changing page identity.
5. Keep browser-page routing distinct from RPC operation routing: web servers consume generated RPC clients, but page files never become RPC operations.

## Authored filesystem contract

The authored web route tree is:

```text
src/pages/
  page.rs                         -> /
  pricing/page.rs                 -> /pricing
  account/[id]/page.rs            -> /account/{id}
  docs/[...slug]/page.rs          -> /docs/{*slug}
  blog/[slug]/
    page.rs                       -> /blog/{slug}
    gen.rs                        -> build-time static path enumeration only
```

A route folder may contain:

```text
x/y/z/
  page.rs                         # required, authored
  gen.rs                          # optional, authored, web-only
```

`gen.rs` is not an API-route file. API route folders remain `route.rs` + `handlers.rs` + generated `rpc.rs` during the current migration period.

## Page attributes are the documentation source

`#[ores_page(...)]` already carries the static metadata needed for page docs: renderer, delivery/render mode, title, summary, auth class, stability, database mode, features, data sources, tags, client source, and revalidation policy.

The next page-doc projection should consume the same analyzed metadata and filesystem route grammar used by the generated Axum router and emit a stable page inventory. No second annotation vocabulary should be introduced.

Recommended generated artifacts:

```text
generated/web/
  page-manifest.json
  pages.md
  pages.html
  routes.rs
```

Each manifest entry should include at least:

```text
canonical_url
source_page_rs
source_gen_rs?
route_shape
route_params
renderer
delivery
render_mode
revalidation
title
summary
auth
stability
database
features[]
data_sources[]
tags[]
source_sha256
manifest_sha256
```

Markdown and HTML are projections of this manifest, not independent authorities.

## Generated Lambda adapters are web-server outputs

A web deployment may project one admitted page route (or a deterministic route group) into a generated Lambda entrypoint. That output should live under `generated/`, not beside authored `page.rs`/`gen.rs`, so generated provider glue cannot be confused with authored page code:

```text
generated/web/lambda/
  account/[id]/lambda.rs
  blog/[slug]/lambda.rs
```

A generated `lambda.rs` is an executable adapter and therefore may own `main`. Its job is narrow:

1. decode the provider event / HTTP request;
2. build the page runtime context;
3. invoke the generated page adapter for the exact filesystem route;
4. encode the provider response;
5. preserve auth, tracing, cache/revalidation, and error semantics already admitted for that page.

It must not contain page business/rendering logic and must never manufacture an RPC operation from the page.

The generated entrypoint should carry a marker such as:

```rust
// @generated by ores-stack web lambda; do not edit
```

and `ores-stack --check` must refuse handwritten or marker-mutated files rather than overwrite them.

## Axum router projection

The monolith web-server build remains an Axum router projection of the same page manifest. URL meaning is always derived from `src/pages/**/page.rs`; a Lambda target and a monolith target therefore share route identity rather than maintaining separate path configuration.

Conceptually:

```text
src/pages/account/[id]/page.rs
            |
            v
api-docs page analysis + #[ores_page] metadata
            |
            +--------------------+
            |                    |
            v                    v
generated Axum router      generated page docs
            |
            v
ores-stack deployment IR
      |               |
      v               v
monolith binary    generated web lambda.rs/main
```

## Relationship to `gen.rs`

`#[ores_generate] pub async fn generate_static_params(...)` remains build-time enumeration. It is valid only as a sibling of a web `page.rs` and must not be discovered through the API `src/routes/**` scanner.

Migration rule: keep the compatibility `GEN_FILE` API export only long enough to avoid an abrupt source break for downstream tooling, but remove `gen_file` from the API `RouteFolderContract` now. Consumers should move to page-specific APIs.

## Relationship to API servers

This proposal deliberately leaves the API-server contract alone:

```text
src/routes/**/
  handlers.rs                     # semantic operation authority
  route.rs                        # optional HTTP projection
  rpc.rs                          # generated RPC glue during migration
```

If API-server Lambda operation adapters continue to exist, they are a separate operation-oriented projection and must use separate manifests/markers/commands from web-page Lambda adapters. The two should not share a vague `lambda.rs` ownership rule merely because both target AWS Lambda.

## Contract authorities

For new web deployment/page-manifest configuration, use independent TypeSpec and JSON Schema Draft 2020-12 peers and admit them with `ORESoftware/typespec-json-schema-validator`. The Rust structs and generated output must then be checked against both peers; TypeSpec must not silently become a JSON-Schema generator or vice versa.

## Proposed command surface

Names are provisional, but responsibilities should stay separate:

```text
api-docs pages inspect
api-docs pages docs --format md|html
api-docs pages manifest --check

ores-stack web inspect
ores-stack web sync
ores-stack web sync --check
ores-stack web lambda plan
ores-stack web lambda generate --check
```

Avoid routing these through `rpc sync` or API-server Lambda commands.

## Rollout

1. Land the page/API boundary cleanup in `api-docs`.
2. Add page-manifest + deterministic Markdown/HTML projection in `api-docs`.
3. Add web deployment IR and web-Lambda renderer in `ores-stack`.
4. Prove one ordinary `*-web-server.rs` and one `*-admin-web-server.rs` canary.
5. Add `*-test` coverage for static, dynamic, catch-all, auth, and Lambda entrypoint shapes.
6. Roll across the remaining web-server repos only after `--check` is deterministic and canaries are clean.

Do not mass-edit the 25 orgs until the authority split and generated-file ownership rules are stable.
