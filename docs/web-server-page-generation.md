# Web-server page generation boundary (draft)

This document is intentionally scoped to `*-web-server.rs` and `*-admin-web-server.rs`. It does **not** redefine the `*-api-server.rs` / `*-admin-api-server.rs` route or RPC contract.

## Reconciled decisions (2026-09-19)

Two sessions drafted this design in parallel and disagreed on a few points. The
five draft PRs are one coordinated set; this block is identical in each and wins
over any older wording elsewhere in the set.

| PR | Owns |
| --- | --- |
| `api-docs#177` | page/API boundary (`gen.rs` leaves `RouteFolderContract`), page manifest + docs from `#[ores_page]` |
| `api-docs#176` | `page_lambda_glue()`: the generated sibling `lambda.rs` source contract |
| `ores-stack#69` | repository role admission, `ores-stack web` manifest/docs/sync, web deployment IR |
| `ores-stack#68` | `ores-stack web lambda`: materialize, build units, AWS/GCP packaging |
| `ores-lambdas-template#35` | provider runtime + Lambda middleware chain in `*-lambdas` |

1. **`lambda.rs` is a sibling of `page.rs`**: `src/pages/x/y/z/{page.rs,gen.rs,lambda.rs}`.
   It is not placed under `generated/web/lambda/`. It is 100% generated, carries
   the marker below, and `--check` refuses an unmarked, hand-edited or symlinked
   file at that path.
2. **One marker, owned by the generator in `api-docs`**:
   `// @generated by ores-api-docs for a *-web-server.rs page; DO NOT EDIT.`
3. **One command tree, `ores-stack web ...`**, with Lambda work nested under it
   so role admission is shared: `web inspect | manifest | docs | sync [--check]`
   and `web lambda plan | sync [--check] | build --provider aws|gcp | package --provider aws|gcp`.
   There is no top-level `web-lambda` command, and nothing hangs off
   `ores-stack rpc ...` or the API-operation `lambda` commands of `ores-stack#65`.
4. **Generated, non-source outputs live under `generated/web/`**, matching the
   existing `generated/rpc/` convention: `generated/web/page-manifest.json`,
   `pages.md`, `pages.html`, and per-unit Cargo build manifests at
   `generated/web/lambda/<unit>/Cargo.toml` whose `[[bin]]` path points back at
   the sibling `src/pages/.../lambda.rs`.
5. **Route discovery is build-time, not runtime.** The Axum router is generated
   from the validated `src/pages/**/page.rs` inventory (`page_router_glue`); no
   server walks the filesystem while serving. `ores-stack dev` re-runs discovery
   when a `page.rs`/`gen.rs` is added, moved or removed.
6. **`lambda.rs` reaches the page through one generated trampoline in the
   web-server library, never by `#[path = "page.rs"]`.** `lambda.rs` is its own
   bin crate root, so re-mounting the page would make every `crate::` path inside
   it resolve against the Lambda bin. Page modules stay **private**; the page
   glue emits one `#[doc(hidden)] pub fn __ores_invoke_page_<stem>_<sha256/16>`
   per page and `lambda.rs` names only that. The digest suffix makes the name
   injective (`a-b` and `a_b` share a readable stem). The build unit aliases the
   product crate to `ores_web_app` and the org `*-lambdas` crate to
   `ores_page_lambda_runtime`; generated source names neither organization. The
   web-server lib exports `pub mod ores_pages` (the generated glue) and
   `pub fn ores_page_lambda_state() -> PageLambdaStateFuture`.
7. **Application state is an explicit, typed ABI.** `PageContext` carries
   type-erased `PageState`; the standalone router gets it from Axum `State<S>`.
   A page Lambda has no router, so generated `main` calls
   `ores_page_lambda_state` (`ores_api_docs_client::PageLambdaStateFn`) once per
   cold start and hands the result to `run_page`. `lambda.rs` assigns both the
   trampoline and the state function to `const`s of their ABI types, so a library
   missing either surface fails the build, not the first request. It must be the
   same constructor the standalone server uses, or the two hosts drift.
8. **One page per Lambda first.** `lambda_route_group` stays in the deployment
   IR as a reserved shape but is not generated until per-page parity is proven;
   a grouped artifact would need a multi-route matcher and breaks the 1:1
   `lambda.rs`-per-`page.rs` rule.
9. **Open seam, not yet built:** per-page response finalization (CSS / JS / WASM
   digests) is baked into the generated Axum handlers today. It must be extracted
   into an Axum-free function both hosts call before a page Lambda can return the
   same bytes as the standalone server. This is the first implementation slice.
10. **A page never acquires RPC-operation identity.** The page manifest records
    what a page calls as `rpc_dependencies[]`, never `rpc_operations[]`.
11. **A build unit is its own Cargo workspace root.** `generated/web/lambda/<unit>/Cargo.toml`
    carries an empty `[workspace]` table so it is never absorbed by, or rejected
    from, the product workspace. Its `Cargo.lock` is seeded from the product lock
    by `web lambda sync`, committed, and every build runs `--locked`.

### Fleet baseline (read-only audit of the local checkouts, 2026-09-19)

Across 268 `*-web-server.rs` / `*-api-server.rs` checkouts: **no repository has a
`src/pages/**/page.rs` tree yet, and no `gen.rs` or `lambda.rs` exists in any
API server.** The `gen.rs` leak into the API side is confined to the `api-docs`
`RouteFolderContract` (fixed in `api-docs#177`), so the rollout is greenfield
adoption rather than a file migration. Local checkouts can be stale; re-run the
audit with `ores-stack web inspect` against fresh clones before acting on it.

## Goals

1. Keep a Next.js-like 1:1 relationship between browser URL paths and Rust source folders.
2. Generate deterministic page documentation from authored Rust attributes without executing page code.
3. Keep `gen.rs` exclusively on the web-page/static-generation side.
4. Let `ores-stack` project an admitted page inventory into monolith, static, or Lambda deployment shapes without changing page identity.
5. Keep browser-page routing distinct from RPC operation routing: web servers consume generated RPC clients, but page files never become RPC operations.

## Authored filesystem contract

The authored web route tree is:

```text
src/pages/
  page.rs                         -> /
  pricing/page.rs                 -> /pricing
  account/[id]/page.rs            -> /account/{id}
  docs/[...slug]/page.rs          -> /docs/{*slug}
  blog/[slug]/
    page.rs                       -> /blog/{slug}
    gen.rs                        -> build-time static path enumeration only
```

A route folder may contain:

```text
x/y/z/
  page.rs                         # required, authored
  gen.rs                          # optional, authored, web-only
  lambda.rs                       # optional, 100% generated (see api-docs#176)
```

`gen.rs` is not an API-route file. API route folders remain `route.rs` + `handlers.rs` + generated `rpc.rs` during the current migration period.

## Page attributes are the documentation source

`#[ores_page(...)]` already carries the static metadata needed for page docs: renderer, delivery/render mode, title, summary, auth class, stability, database mode, features, data sources, tags, client source, and revalidation policy.

The next page-doc projection should consume the same analyzed metadata and filesystem route grammar used by the generated Axum router and emit a stable page inventory. No second annotation vocabulary should be introduced.

Recommended generated artifacts:

```text
generated/web/
  page-manifest.json
  pages.md
  pages.html
  routes.rs
```

Each manifest entry should include at least:

```text
canonical_url
source_page_rs
source_gen_rs?
route_shape
route_params
renderer
delivery
render_mode
revalidation
title
summary
auth
stability
database
features[]
data_sources[]
tags[]
source_sha256
manifest_sha256
```

Markdown and HTML are projections of this manifest, not independent authorities.

## Generated Lambda adapters are web-server outputs

A web deployment may project one admitted page route into a generated Lambda entrypoint. It is materialized as a sibling of the page it serves, so the folder stays the single place a route is defined:

```text
src/pages/account/[id]/{page.rs,lambda.rs}
src/pages/blog/[slug]/{page.rs,gen.rs,lambda.rs}
```

The sibling file cannot be confused with authored code because it is marker-owned, refused when unmarked or symlinked, and never edited by hand. The exact source contract is `docs/web-page-lambda-contract.md` (`api-docs#176`).

A generated `lambda.rs` is an executable adapter and therefore may own `main`. Its job is narrow:

1. decode the provider event / HTTP request;
2. build the page runtime context;
3. invoke the generated page adapter for the exact filesystem route;
4. encode the provider response;
5. preserve auth, tracing, cache/revalidation, and error semantics already admitted for that page.

It must not contain page business/rendering logic and must never manufacture an RPC operation from the page.

The generated entrypoint carries the marker emitted by `page_lambda_glue()`:

```rust
// @generated by ores-api-docs for a *-web-server.rs page; DO NOT EDIT.
```

and `ores-stack --check` must refuse handwritten or marker-mutated files rather than overwrite them.

## Axum router projection

The monolith web-server build remains an Axum router projection of the same page manifest. URL meaning is always derived from `src/pages/**/page.rs`; a Lambda target and a monolith target therefore share route identity rather than maintaining separate path configuration.

Conceptually:

```text
src/pages/account/[id]/page.rs
            |
            v
api-docs page analysis + #[ores_page] metadata
            |
            +--------------------+
            |                    |
            v                    v
generated Axum router      generated page docs
            |
            v
ores-stack deployment IR
      |               |
      v               v
monolith binary    generated web lambda.rs/main
```

## Relationship to `gen.rs`

`#[ores_generate] pub async fn generate_static_params(...)` remains build-time enumeration. It is valid only as a sibling of a web `page.rs` and must not be discovered through the API `src/routes/**` scanner.

Migration rule: removing a public struct field is a Rust source break for any downstream struct literal or exhaustive pattern, even with the constant retained. So `RouteFolderContract::gen_file` and `GEN_FILE` are both kept for one release as `#[deprecated]` compatibility surface — `gen_file` is documented as always `None` for an API route folder, and nothing in `api-docs` reads or sets it. Both are deleted in the following release, called out as a breaking change. New code uses the page-specific contract (`src/pages/**/{page.rs,gen.rs}`).

## Relationship to API servers

This proposal deliberately leaves the API-server contract alone:

```text
src/routes/**/
  handlers.rs                     # semantic operation authority
  route.rs                        # optional HTTP projection
  rpc.rs                          # generated RPC glue during migration
```

If API-server Lambda operation adapters continue to exist, they are a separate operation-oriented projection and must use separate manifests/markers/commands from web-page Lambda adapters. The two should not share a vague `lambda.rs` ownership rule merely because both target AWS Lambda.

## Contract authorities

For new web deployment/page-manifest configuration, use independent TypeSpec and JSON Schema Draft 2020-12 peers and admit them with `ORESoftware/typespec-json-schema-validator`. The Rust structs and generated output must then be checked against both peers; TypeSpec must not silently become a JSON-Schema generator or vice versa.

## Proposed command surface

Names are provisional, but responsibilities should stay separate:

```text
api-docs pages inspect
api-docs pages docs --format md|html
api-docs pages manifest --check

ores-stack web inspect
ores-stack web sync
ores-stack web sync --check
ores-stack web lambda plan
ores-stack web lambda sync --check
```

Avoid routing these through `rpc sync` or API-server Lambda commands.

## Rollout

1. Land the page/API boundary cleanup in `api-docs`.
2. Add page-manifest + deterministic Markdown/HTML projection in `api-docs`.
3. Add web deployment IR and web-Lambda renderer in `ores-stack`.
4. Prove one ordinary `*-web-server.rs` and one `*-admin-web-server.rs` canary.
5. Add `*-test` coverage for static, dynamic, catch-all, auth, and Lambda entrypoint shapes.
6. Roll across the remaining web-server repos only after `--check` is deterministic and canaries are clean.

Do not mass-edit the 25 orgs until the authority split and generated-file ownership rules are stable.
