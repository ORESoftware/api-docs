# Web page Lambda contract — draft

> **Scope: `*-web-server.rs` / `*-admin-web-server.rs` only. This is not the API-server Lambda/RPC contract.**

A browser URL is owned by its authored page folder:

```text
src/pages/x/y/z/
  page.rs      # authored page and routing authority
  gen.rs       # optional authored build-time static enumeration
  lambda.rs    # generated provider-neutral page-function module
```

`page.rs` is the only routing authority. `lambda.rs` is a deterministic deployment/build projection of that page. It never creates an RPC operation, provider runtime, or second path definition.

## Reconciled architecture

The coordinated draft set is:

| PR | Owns |
| --- | --- |
| `api-docs#177` | page/API boundary and page docs/manifest direction |
| `api-docs#176` | generated page ABI, sibling provider-neutral `lambda.rs`, shared response finalization |
| `ores-stack#69` | repository-role admission, web manifest/docs/deployment IR, source sync/check |
| `ores-stack#68` | web Lambda materialization/build/package orchestration |
| `ores-lambdas-template#35` | provider HTTP lifecycle, request/response normalization, provider wrappers/runtime |

The settled rules are:

1. `lambda.rs` is a generated sibling of `page.rs`.
2. `api-docs` owns the generated marker: `// @generated by ores-api-docs for a *-web-server.rs page; DO NOT EDIT.`
3. The sibling `lambda.rs` is **provider-neutral**. It does not contain `main()`, AWS/GCP feature gates, provider SDK imports, `PORT` handling, or provider event types.
4. Provider-specific `main.rs` wrappers are generated only in ignored build trees owned by the `*-lambdas`/build layer, for example `*-lambdas/build/lambda/{aws,gcp}/funcs/web/<id>/main.rs`.
5. All orchestration lives under `ores-stack web ...`; web pages do not use API/RPC Lambda commands.
6. Route discovery is build-time. No serving process walks the filesystem to find pages.
7. Page modules remain private. Cross-crate Lambda access uses generated digest-suffixed trampolines.
8. Application state, page invocation and response finalization are explicit typed ABIs.
9. One page identity maps to one generated page-function module. Optional catch-all routes may have multiple matching path templates without becoming multiple functions.
10. A page manifest may record `rpc_dependencies[]`, but a page never acquires RPC-operation identity.
11. Generated build/package artifacts use immutable revisions and Cargo-generated lockfiles; release compilation uses `--locked`.

## Public web-library ABI

A web-server library exporting generated page Lambda support provides:

```rust
pub mod ores_pages {
    include!(concat!(env!("OUT_DIR"), "/ores_pages.rs"));
}

pub fn ores_page_lambda_state() -> ores_api_docs_client::PageLambdaStateFuture {
    // Build exactly the application state used by the standalone server.
    // Provider wrappers call this once per cold start.
    # todo!()
}
```

The generated `ores_pages` module keeps each authored `page.rs` module private. It exports two `#[doc(hidden)]` functions per page:

```text
__ores_invoke_page_<readable-stem>_<sha256(source-path)/16>
__ores_finalize_page_<readable-stem>_<sha256(source-path)/16>
```

The digest suffix is mandatory because readable normalization is lossy (`a-b` and `a_b` otherwise collide).

The functions are compile-time asserted as:

```rust
ores_api_docs_client::PageFn
ores_api_docs_client::PageFinalizeFn
```

and the state constructor is asserted as:

```rust
ores_api_docs_client::PageLambdaStateFn
```

## Shared response finalization

Response finalization is an explicit Axum-free client ABI:

```rust
pub struct PageResponseAssets<'a> {
    pub css_href: Option<&'a str>,
    pub wasm_sha256: Option<&'a str>,
    pub js_src: Option<&'a str>,
}

pub struct PageResponseRequestHints<'a> {
    pub wasm_have: Option<&'a str>,
    pub dev_reload_script: Option<&'a str>,
}

pub struct FinalizedPageResponse {
    pub status: u16,
    pub headers: Vec<(String, String)>,
    pub body: Vec<u8>,
}

pub type PageFinalizeFn =
    for<'a> fn(PageResult, PageResponseRequestHints<'a>) -> FinalizedPageResponse;
```

`page_router_glue` emits one hidden finalizer trampoline per page. That trampoline closes over the same admitted asset metadata used by standalone Axum: CSS public path, finalized WASM digest and JS public path.

Both hosts therefore share the same page and finalizer:

```text
standalone Axum
  page.rs -> PageResult -> PageFinalizeFn -> FinalizedPageResponse -> Axum Response

provider build wrapper
  provider request -> PageContext -> generated lambda.rs::run
                   -> PageFinalizeFn -> FinalizedPageResponse
                   -> provider response envelope
```

Provider runtimes must not rediscover CSS/WASM metadata or duplicate HTML mutation logic.

## Generated sibling `lambda.rs`

One generated page-function module has this shape:

```rust
// @generated by ores-api-docs for a *-web-server.rs page; DO NOT EDIT.
// WEB SERVER PAGE LAMBDA MODULE ONLY — provider main() is generated elsewhere.
// No RPC surface is introduced by this file.

pub const ORES_PAGE_SOURCE: &str = "src/pages/x/y/z/page.rs";
pub const ORES_PAGE_ROUTE: &str = "/x/y/z";
pub const ORES_PAGE_AXUM_PATHS: &[&str] = &["/x/y/z"];

const __ORES_PAGE: ::ores_api_docs_client::PageFn =
    ::ores_web_app::ores_pages::__ores_invoke_page_<stem>_<digest>;
const __ORES_PAGE_FINALIZE: ::ores_api_docs_client::PageFinalizeFn =
    ::ores_web_app::ores_pages::__ores_finalize_page_<stem>_<digest>;
const __ORES_PAGE_STATE: ::ores_api_docs_client::PageLambdaStateFn =
    ::ores_web_app::ores_page_lambda_state;

pub async fn init_state() -> Result<
    ::ores_api_docs_client::PageState,
    ::ores_api_docs_client::PageLambdaStateError,
> {
    __ORES_PAGE_STATE().await
}

pub async fn run(
    context: ::ores_api_docs_client::PageContext,
    hints: ::ores_api_docs_client::PageResponseRequestHints<'_>,
) -> ::ores_api_docs_client::FinalizedPageResponse {
    let result = __ORES_PAGE(context).await;
    __ORES_PAGE_FINALIZE(result, hints)
}
```

The generated source contains no `main()`, no provider feature selection, and no dependency on `ores_page_lambda_runtime`.

`lambda.rs` also never mounts `page.rs` directly. Re-mounting an authored page from another crate root would change the meaning of every `crate::...` reference in that page. The generated module reaches the page only through the web-server library alias `ores_web_app` and typed trampolines.

## Provider wrapper boundary

AWS/GCP selection belongs outside server source.

The build/package layer materializes a tiny provider-specific wrapper in an ignored build tree. Conceptually:

```rust
#[path = "<exact generated server lambda.rs>"]
mod generated_lambda;

#[tokio::main]
async fn main() -> Result<(), RuntimeError> {
    let state = generated_lambda::init_state().await?;
    provider_runtime::run_page(state, |state, normalized_request| async move {
        let context = build_page_context(state, normalized_request)?;
        let finalized = generated_lambda::run(
            context,
            ores_api_docs_client::PageResponseRequestHints::default(),
        )
        .await;
        provider_response(finalized)
    })
    .await
}
```

The wrapper is generated from the same deterministic template used by conformance tests. Test and deployment mains must not drift.

Provider-specific code owns only:

- runtime/listener/event lifecycle;
- bounded request decoding;
- trusted provider/ingress provenance;
- HTTP method/path/header/cookie/body normalization;
- auth/session middleware when that ABI is supported;
- provider response-envelope conversion;
- provider telemetry/deadline context.

It does not own page routing authority, page behavior, CSS/WASM mutation, or RPC identity.

## Build/package layout

The source repo keeps authored/generated server source only:

```text
src/pages/x/y/z/
  page.rs
  gen.rs
  lambda.rs
```

Non-source planning/evidence may live under `generated/web/`, but provider executables and wrappers live in ignored `*-lambdas/build/` trees, for example:

```text
*-lambdas/build/lambda/aws/funcs/web/<function-id>/
  lambda.rs       # exact source evidence or path-bound copy
  main.rs         # generated AWS wrapper
  Cargo.toml      # isolated generated build package
  Cargo.lock      # Cargo-generated/pinned lock
  artifact/
  receipt.json

*-lambdas/build/lambda/gcp/funcs/web/<function-id>/
  lambda.rs
  main.rs
  Cargo.toml
  Cargo.lock
  artifact/
  receipt.json
```

Provider wrappers/build manifests bind the exact server source SHA, page identity, generated lambda digest, api-docs revision, provider, architecture, runtime revision and toolchain. Ordinary source sync does not deploy or mutate cloud resources.

## `ores-stack web lambda` semantics

The intended command family is:

```text
ores-stack web lambda plan
ores-stack web lambda sync
ores-stack web lambda sync --check
ores-stack web lambda build --provider aws|gcp
ores-stack web lambda package --provider aws|gcp
```

`sync` updates/checks deterministic source/deployment projections. `--check` is read-only and must regenerate the expected outputs and fail on missing, stale, authored/unmarked, symlinked, or lock-drifted artifacts. It must not merely ask Cargo whether an existing lockfile happens to be self-consistent.

Any multi-file sync is failure-atomic at repository scope: compute and validate everything first; if a later write/build-lock step fails, restore the prior complete set rather than leaving a mixed generation.

## Compile/conformance proof

`rust/tests/page_lambda_compile_fixture.rs` proves the intended ownership topology:

- private authored page module;
- authored page using `crate::...` paths;
- application state supplied through `PageLambdaStateFn`;
- full page-router glue including the per-page `PageFinalizeFn`;
- generated sibling provider-neutral `lambda.rs`;
- an isolated temporary Cargo package;
- tiny external AWS/GCP-style provider mains generated outside server source;
- both mains execute the same generated page-function bytes and produce the same finalized page response.

The fixture intentionally does **not** make the server `lambda.rs` itself an executable or provider-aware module.

## Security and reproducibility invariants

- Generated server source contains no provider credentials or mutable deployment secrets.
- Client headers cannot manufacture trusted provider identity.
- Unsupported authenticated/admin deployment fails closed until shared auth/session middleware is present and proven.
- `PageError` details are server telemetry and are not reflected to browsers.
- A web page does not gain database write authority merely because it is deployed as a Lambda.
- `gen.rs` remains build-time only and is never exposed as a request handler.
- Runtime/source dependencies use immutable revisions; lockfiles are produced by Cargo, committed where required, and verified by exact regeneration in check mode.
- Generated writes refuse symlink traversal and authored-file replacement.
- Exact-head evidence is required: consumer pins and conformance evidence must identify the exact reviewed api-docs/runtime source revision.

## Rollout

1. Land the web/page authority boundary and provider-neutral ABI in `api-docs`.
2. Land `ores-stack web` role admission, manifests, deterministic source sync and exact check mode.
3. Materialize provider wrappers/build packages only in the `*-lambdas` build layer.
4. Prove one ordinary public web server through standalone/AWS/GCP parity fixtures.
5. Keep session/admin page deployment blocked until shared auth/session middleware is carried through the provider wrapper and tested.
6. Expand through matching `*-test` repos, then 3–5 varied orgs.
7. Roll fleet-wide only after deterministic check mode, locked builds, exact-source receipts and response parity remain green.
